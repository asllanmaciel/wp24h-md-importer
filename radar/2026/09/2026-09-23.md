# Radar Estratégico — WP24H MD Importer — 2026-09-23

## P1 — Workflow de compatibilidade manual ainda usa `actions/checkout@v4` no fim da janela Node 20

### Prioridade

**P1**

### O que aconteceu

O GitHub marcou **23/09/2026** como data de remoção do Node 20 dos Actions runners. `actions/checkout@v4` declara `runs.using: node20`; o checkout v7 usa Node 24.

### Impacto específico no projeto

`.github/workflows/php-lint.yml` continua usando `actions/checkout@v4`. O workflow está pausado para execução automática e roda via `workflow_dispatch`, mas continua sendo uma ferramenta real de validação antes de releases/compatibility checks.

Isso significa que o risco não é frequência, e sim confiabilidade justamente quando o workflow for acionado para qualificar uma nova versão do WordPress.

### Risco / oportunidade

**Risco P1:** o gate manual de lint/compatibilidade falhar ou operar em runtime fora da janela suportada quando mais for necessário.

**Oportunidade P1:** qualificar a Action Node 24 junto da próxima rodada de WordPress e eliminar uma dívida já conhecida no material de CI.

### Evidência / fontes

- GitHub Changelog: https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/
- `checkout@v4`: https://github.com/actions/checkout/blob/v4/action.yml
- `checkout@v7`: https://github.com/actions/checkout/blob/v7/action.yml
- Workflow atual: https://github.com/asllanmaciel/wp24h-md-importer/blob/main/.github/workflows/php-lint.yml

### Ação recomendada

1. migrar checkout para a linha Node 24 atualmente suportada;
2. executar manualmente a matrix PHP existente e registrar GREEN no SHA exato;
3. inventariar outros JavaScript Actions antes de considerar o runtime debt fechado;
4. não reativar execução automática apenas por causa desta migração; cadence e runtime são decisões separadas.

## P2 — WordPress 7.1.2 deve substituir 7.1 como próximo target do compatibility harness

### Prioridade

**P2**

### O que aconteceu

O WordPress publicou em **22/09/2026** a versão **7.1.2**, recomendando atualização imediata por corrigir a CVE-2026-87902 / GHSA-7hp8-65ch-5whp, classificada como crítica.

### Impacto específico no projeto

O plugin atualmente declara `Tested up to: 7.1` e já possui um compatibility harness desenhado para impedir alteração de metadata sem evidence real.

Como `7.1.2` é agora o patch seguro atual da série 7.1, ele deve ser o próximo candidate runtime. Isso não significa que o importer seja vulnerável ou incompatível; significa que a alegação de compatibilidade deve ser renovada contra a security stable atual.

### Risco / oportunidade

**Risco P2:** manter a metadata semanticamente atrás da versão segura atual ou avançá-la sem executar o harness.

**Oportunidade P2:** combinar a migração de CI com uma qualification real em WordPress 7.1.2 e preservar versão exata/PHP/plugin SHA como evidence.

### Evidência / fontes

- WordPress 7.1.2: https://wordpress.org/news/2026/09/wordpress-7-1-2-release/
- Advisory: https://github.com/WordPress/wordpress-develop/security/advisories/GHSA-7hp8-65ch-5whp
- `readme.txt`: https://github.com/asllanmaciel/wp24h-md-importer/blob/main/readme.txt
- Compatibility design: https://github.com/asllanmaciel/wp24h-md-importer/blob/main/docs/superpowers/specs/2026-08-21-wp-compatibility-harness-design.md

### Ação recomendada

1. executar o compatibility harness contra WordPress 7.1.2;
2. registrar versão do Core, PHP, plugin SHA, checks e resultado;
3. só então decidir se `Tested up to` deve permanecer `7.1` ou avançar conforme a convenção publicada pelo WordPress.org;
4. manter qualquer falha como `BLOCKED/FAIL`, nunca converter indisponibilidade de ambiente em PASS.

## Invariante para o analyzer

`workflow manual` ainda é runtime operacional; `Tested up to` é uma alegação de evidence, não um reflexo automático da versão mais recente do WordPress.
