# Radar Estratégico — WP24H MD Importer — 2026-09-13

## P2 — WordPress.org agora pode bloquear automaticamente uma release antes de distribuí-la

### Prioridade

**P2**

### O que aconteceu

Em **09/09/2026**, o WordPress Plugins Team formalizou um **automated security review para toda nova release de plugin hospedado no WordPress.org**. Durante o cooldown — atualmente de **6 horas** — as mudanças são analisadas por vários modelos de IA junto do Jetpack Scan. Releases abaixo do limiar seguem o fluxo normal; releases com score de alto risco são bloqueadas antes de chegar à WordPress.org update API e todos os committers recebem email com os findings.

O WordPress deixa explícito que score alto mede **risco, não intenção** e que falsos positivos ainda podem ocorrer. Um bloqueio afeta apenas aquela versão: o plugin continua publicado e a versão anteriormente distribuída permanece disponível. Para um finding real, o caminho recomendado é corrigir e publicar uma nova versão, que passa novamente pelo cooldown e pela revisão.

### Impacto específico no projeto

Este repositório declara que o **WP24H MD Importer foi desenhado para permanecer apto à submissão ao WordPress.org Plugin Directory**. A versão atual é **1.2.0**, ainda sem tag/release GitHub publicada, e o README já aponta uma validação limpa de runtime/ZIP como gate antes da primeira release.

A nova etapa do WordPress.org muda a semântica do release process: **commit/tag/SVN não significam mais distribuição**. Entre publicar a versão e ela aparecer na update API existe agora um estado externo de cooldown/review que pode terminar em `distributed` ou `blocked`.

Isso é especialmente relevante antes da primeira distribuição oficial porque o projeto já possui checks locais de capabilities, nonces, sanitização, escaping, REST autenticado e download seguro de imagem; esses checks continuam necessários, mas não substituem nem antecipam o resultado do review do diretório.

### Risco / oportunidade

**Risco P2:** marcar uma versão como "shipped" imediatamente após commit/tag/SVN e automatizar anúncio ou rollout antes de a WordPress.org update API realmente oferecê-la.

**Risco P2:** tratar ausência imediata de email como aprovação antes do término do cooldown.

**Oportunidade P2:** transformar o novo review em mais um gate observável do release pipeline, preservando localmente evidência de package/metadata/runtime e externamente o estado de distribuição.

### Ação recomendada

Antes da primeira publicação no WordPress.org, evoluir o runbook de release para representar estados separados, por exemplo:

`package_built → local_validated → svn_committed → wordpress_review_pending → distributed | blocked`

E registrar como evidence pelo menos versão, hash do ZIP validado, revisão/metadados locais, instante do commit/tag, início do cooldown e o primeiro fato observável de distribuição ou bloqueio.

Não promover uma versão para `distributed` por tempo decorrido ou silêncio do serviço; confirmar que a versão está efetivamente disponível na update API/diretório. Se houver bloqueio, preservar o finding recebido, corrigir a causa e publicar uma nova versão em vez de tratar o score como prova de intenção maliciosa.

O `wp-plugin-readme-validator` continua útil como gate determinístico de metadados, mas um resultado verde nele deve continuar significando somente **metadata contract válido**, nunca `security_review_passed` ou `distributed`.
